## 从“能演示”到“可验证、可部署、可复现”

## 每节重点规划

### 5.1 制定测试计划：把“试一下”变成可执行验证

**重点内容：**
- 从需求、用户故事、业务规则、接口和页面中提取测试点；
- 划分测试范围：核心流程、权限、状态、异常、边界值、兼容性；
- 确定优先级：阻断演示的问题优先于样式优化；
- 准备测试账号、测试数据、数据库恢复方式和测试环境；
- 明确“不测什么”：暂不支持的浏览器、非课程范围的高并发、安全渗透等。

**建议成果：**
- 《测试计划》
- 核心流程测试点清单
- 测试环境与账号说明

**关键提示：**
> 不是把所有按钮点一遍，而是验证每一条需求、业务规则和状态转换是否真正成立。

---

### 5.2 编写并执行测试：验证正常、异常和越权

**重点内容：**
- 测试用例结构：编号、前置条件、操作步骤、预期结果、实际结果；
- 页面功能测试；
- Apifox / Postman 接口测试；
- 正常路径、失败路径与边界条件；
- 登录、未登录、普通用户、管理员等角色权限测试；
- 多角色核心业务流程的端到端验证；
- 测试截图、接口响应和日志作为证据保存。

**建议成果：**
- 《测试用例》
- 接口测试集合或导出记录
- 测试执行记录

**最低覆盖要求：**
1. 一条核心业务流程的正常路径；
2. 至少一个失败或异常路径；
3. 未登录与越权访问；
4. 空数据、重复提交、非法状态等典型边界；
5. 部署后重新执行核心流程。

---

### 5.3 管理缺陷并回归：让修复可追踪

**重点内容：**
- 缺陷描述规范：现象、复现步骤、预期结果、实际结果、影响范围；
- 缺陷优先级：阻断、严重、一般、建议；
- 找根因：页面、接口、业务规则、数据库、权限或环境配置；
- 修复后进行回归测试；
- 关联 Git 提交，避免“改了但不知道改了什么”。

**建议成果：**
- 缺陷清单
- 修复与回归记录
- 关键问题的 Git 提交链接或提交号

**建议缺陷表字段：**

| 编号 | 问题描述 | 严重程度 | 复现步骤 | 修复方式 | 回归结果 | 对应提交 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |

---

### 5.4 完成部署准备：确保换一台机器也能启动

**重点内容：**
- 开发配置与部署配置分离；
- 环境变量、数据库地址、端口、账号密码等敏感配置管理；
- 数据库初始化脚本、迁移脚本与测试数据；
- Dockerfile、`docker-compose.yml`、Nginx 配置；
- 静态资源、上传文件和日志目录；
- 数据库备份与恢复；
- 部署前检查清单。

**建议成果：**
- 部署说明
- `.env.example` 或配置说明文档
- 初始化 SQL / 数据迁移脚本
- Docker Compose 配置

**最低要求：**
> 在不依赖 IDE、不手动修改代码的前提下，按 README 与部署说明，从空数据库启动项目。

---

### 5.5 部署并验证系统：本地部署为最低要求

**最低部署要求：**
- 在学生本人电脑、实验室电脑或局域网环境完成部署；
- 使用 Docker 完成数据库与项目服务启动，或按技术路线完成等价部署；
- 浏览器通过部署地址访问系统；
- 部署后执行一次完整核心流程；
- 保存启动命令、访问地址、关键截图和问题记录。

**进阶部署方向：**
- Linux 云服务器；
- Nginx 反向代理；
- 域名与 HTTPS；
- Docker 镜像构建与容器日志；
- 自动化部署脚本；
- 公网可访问演示地址。

**建议成果：**
- 部署记录
- 部署验证截图或录屏
- 核心流程部署后测试结果
- 可选：局域网 / 公网访问地址

---

### 5.6 整理交付成果：形成 `v1.0` 可复现版本

**重点内容：**
- 完善项目 README；
- 整理运行说明、账号说明、功能清单、技术栈和项目截图；
- 汇总需求、设计、测试、部署文档；
- 清理无关文件、敏感信息、调试代码与无效账号；
- 创建 Git Tag，例如 `v1.0.0`；
- 根据交付清单进行最终检查。

**README 最低内容：**
- 项目简介与真实问题背景；
- 功能与角色说明；
- 技术栈；
- 项目结构；
- 本地启动与 Docker 部署步骤；
- 数据库初始化方式；
- 测试账号；
- 系统截图；
- 项目文档与演示链接；
- 已知限制与后续改进方向。

**建议成果：**
- 《测试报告》
- 《部署说明》
- 完整项目 README
- `v1.0` 可交付版本
- 最终交付清单
