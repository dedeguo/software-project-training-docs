# 第六篇：项目展示、答辩与成长复盘

## 从“完成项目”到“讲清成果、沉淀能力”

第五篇完成后，你的项目已经具备可运行、可部署、可测试的 `v1.0` 版本。但项目成果如果只停留在代码仓库里，他人难以理解其价值，你自己也难以将其转化为求职、毕业设计或后续学习的资产。

第六篇将帮助你把项目成果转化为**可展示、可解释、可复用的个人资产**：演示材料、答辩表现、个人贡献说明、简历素材和复盘记录。本篇不再是“继续开发”，而是“把已经做完的事，用别人能看懂的方式讲出来”。

!!! quote "本篇核心任务"
    用演示让别人看懂项目价值；用答辩让别人相信你真的完成了项目；用个人贡献说明让别人知道你能做什么；用简历和作品集让成果可复用；用复盘让经验可迁移。

---

## 一、你现在处于什么阶段

完成第五篇后，项目通常处于 `v1.0`：功能稳定、部署可复现、测试有证据。但可能存在如下情况：

```text
✅ 项目可以运行、可以部署、有测试报告
✅ 有 README、Git 标签和基础文档

⚠️ 没有演示视频，别人无法快速了解项目
⚠️ 没有答辩准备，讲不清为什么这样做
⚠️ 多人项目中，个人贡献不明确
⚠️ 简历上只有“负责 XX 模块开发”，无法证明能力
⚠️ 没有复盘，经验无法迁移到下一个项目
```

本篇结束后，你应形成：

```text
✅ 3—5 分钟演示视频，让别人快速看懂项目
✅ 答辩 PPT 和 Q&A 准备，能清晰陈述项目价值
✅ 个人贡献说明，明确自己在团队中的角色和成果
✅ 简历项目描述和作品集链接，可复用于求职
✅ 项目复盘报告，记录经验、差距和后续计划
```

---

## 二、本篇学习目标

完成本篇后，你应能够：

1. 制作 3—5 分钟演示视频，清晰展示项目定位、核心功能和技术亮点；
2. 准备演示脚本和环境检查清单，确保演示过程稳定可靠；
3. 完成答辩 PPT 和陈述，回答“做了什么、为什么这样做、遇到什么问题、如何验证”；
4. 明确个人在项目中的具体贡献，并用证据支持；
5. 将项目成果转化为简历描述、作品集链接和面试表达；
6. 完成项目复盘，识别经验、差距和后续行动计划。


## 四、演示不是“把功能点一遍”

演示的目标是**用最少的时间，让观看者理解项目解决什么问题、谁在用、怎么用、效果如何**。

### 演示视频的建议结构

| 时间 | 内容 | 目的 |
| :--- | :--- | :--- |
| 0—10s | 项目定位：为谁解决什么问题 | 让观看者快速理解项目价值 |
| 10—70s | 核心功能：主要业务流程和关键界面 | 展示项目能做什么 |
| 70—90s | 技术亮点：架构、关键技术、难点解决 | 体现技术深度 |
| 90—100s | 部署访问：实际运行效果 | 证明项目可复现 |

### 演示脚本的关键要素

- **先说什么**：项目定位（一句话）；
- **后说什么**：核心功能（按业务流程顺序）；
- **重点强调**：技术亮点和解决的问题；
- **避免什么**：逐个菜单点击、无目的的页面跳转、解释每个按钮的作用。

### 演示环境检查清单

- [ ] 网络连接稳定（如使用在线部署）；
- [ ] 测试账号可用，密码已确认；
- [ ] 数据库已初始化，测试数据完整；
- [ ] 浏览器已清理缓存，无插件干扰；
- [ ] 屏幕分辨率适合演示（建议 1920×1080）；
- [ ] 字体大小适中，关键内容可读；
- [ ] 已准备备用方案（录屏 / 本地部署 / 截图）。

---

## 五、答辩不是“背稿”

答辩的目标是**用清晰逻辑和真实证据，让别人相信你真的完成了这个项目，并且理解为什么这样做**。

### 答辩的核心结构

| 部分 | 内容 | 时间占比 |
| :--- | :--- | :--- |
| 问题背景 | 项目解决什么问题、为什么值得做 | 10% |
| 需求分析 | 目标用户、核心功能、业务规则 | 15% |
| 系统设计 | 架构、关键技术、数据库设计 | 20% |
| 实现与测试 | 核心功能实现、测试验证、缺陷修复 | 25% |
| 部署与成果 | 部署方式、运行效果、已知限制 | 15% |
| 总结与展望 | 项目价值、个人成长、后续计划 | 15% |

### 高频问题与回答策略

| 问题 | 回答要点 |
| :--- | :--- |
| 为什么选择这个题目？ | 问题真实、可验证、范围可控；有明确的用户和业务场景 |
| 为什么用这个技术栈？ | 能力匹配、生态成熟、课程要求；对比过其他方案 |
| 遇到过什么困难？怎样解决？ | 具体例子、根因分析、最小修复、回归验证 |
| 哪些地方做得不够好？ | 诚实承认、说明原因、后续改进计划 |
| 如果重新做，会怎么改进？ | 具体的技术或流程改进，不是空泛的“更努力” |

### Q&A 准备清单

提前列出可能被问到的 10—15 个问题，并准备回答要点：

- 技术选型类：为什么用 XX 不用 XX？
- 架构设计类：为什么这样分层？为什么这样设计数据库？
- 实现细节类：XX 功能是怎么实现的？遇到什么难点？
- 测试验证类：怎么保证系统正确？测试覆盖了哪些场景？
- 部署运维类：怎么部署？遇到什么问题？怎么解决？
- 个人贡献类：你在团队中负责什么？遇到冲突怎么解决？

---

## 六、个人贡献不是“我写了多少行代码”

个人贡献的目标是**让别人知道你在项目中解决了什么问题、做出了什么决策、承担了什么责任、获得了什么成长**。

### 个人贡献的三个维度

| 维度 | 内容 | 证据 |
| :--- | :--- | :--- |
| 技术贡献 | 负责的模块、关键技术决策、解决的问题 | Git 提交记录、设计文档、代码评审记录 |
| 过程贡献 | 需求分析、设计评审、测试验证、部署实施 | 需求文档、测试报告、部署记录 |
| 协作贡献 | 沟通协调、文档编写、代码审查、经验分享 | 会议纪要、文档链接、代码审查记录 |

### 个人贡献说明的结构

```text
背景：项目是什么、团队多少人、我在团队中的角色
→ 我的职责：具体负责哪些模块、哪些决策
→ 关键成果：完成了什么、解决了什么问题、验证了什么
→ 遇到的问题：具体困难、根因分析、解决过程
→ 学到什么：新技能、新方法、新认知
```

### 能力证明的方式

- **Git 提交记录**：代码贡献的直接证据；
- **关键设计文档**：架构决策的思考过程；
- **测试报告**：质量保障的具体成果；
- **演示视频**：沟通表达的能力展示；
- **复盘报告**：反思能力和持续改进的证据。

---

## 七、简历项目不是“罗列功能”

简历项目的目标是**证明你能用技术解决真实问题，并且能把过程和结果讲清楚**。

### 简历项目描述的结构

```text
项目名称：一句话说明项目定位
→ 解决的问题：为谁解决什么问题、为什么值得做
→ 技术栈：使用的关键技术、框架和工具
→ 我的贡献：具体负责的模块、关键决策、解决的问题
→ 量化成果：可验证的结果、测试覆盖率、部署状态
```

### 简历项目描述的写法

**避免：**

```text
负责 XX 模块开发，使用 Spring Boot 和 Vue 实现。
```

**推荐：**

```text
设计并实现校园失物招领平台的认领审核模块，支持失主、拾到者和管理员的多角色协作流程；
通过 JWT 鉴权和角色权限控制，确保数据安全；
编写 15 个测试用例覆盖正常、异常和权限场景，缺陷修复率 100%；
使用 Docker Compose 实现一键部署，支持本机和局域网访问。
```

### 作品集的组成

- **项目 README**：运行入口，让别人能快速启动项目；
- **演示视频**：观看入口，让别人能快速了解项目；
- **关键设计文档**：思考入口，让别人理解你的架构决策；
- **测试报告**：质量入口，让别人相信你的项目可靠；
- **部署地址**：体验入口，让别人能实际使用你的项目。

### 面试表达的准备

- **30 秒电梯陈述**：项目一句话 + 核心价值；
- **2 分钟项目介绍**：背景、功能、技术、成果；
- **5 分钟深入讨论**：架构决策、难点解决、测试策略；
- **常见追问的预演**：为什么这样做、还有什么方案、遇到过什么问题。

---

## 八、复盘不是“自我批评”

复盘的目标是**客观分析项目中的经验和教训，让经验可迁移，让改进可持续**。

### 复盘的四个问题

| 问题 | 目的 | 示例 |
| :--- | :--- | :--- |
| 做得好 | 识别超出预期的做法，形成可复制经验 | 提前冻结需求基线，避免了后期大范围返工 |
| 做得不好 | 识别低于预期的地方，明确改进方向 | 测试计划制定太晚，导致部分功能没有充分测试 |
| 学到什么 | 沉淀新技能、新方法、新认知 | 学会了使用 Docker Compose 编排多服务部署 |
| 下次怎样做得更好 | 制定具体行动计划，确保持续改进 | 下个项目中，测试计划与需求分析同步进行 |

### 能力差距分析

```text
当前能力：能独立完成 Spring Boot + Vue 项目，具备基础测试和部署能力
→ 目标能力：能设计高并发架构，具备性能优化和安全防护能力
→ 差距：缺乏高并发场景经验，对性能测试和安全测试不熟悉
→ 弥补方案：学习 JMeter 性能测试，阅读《高并发系统设计》，参与开源项目
```

### 后续行动计划

- **毕业设计**：选择更复杂的业务场景，应用本次项目经验；
- **竞赛**：参加软件设计竞赛，锻炼快速原型和演示能力；
- **求职**：完善简历和作品集，准备技术面试；
- **开源贡献**：参与开源项目，学习大型项目的协作方式。

## 九、本篇最低交付标准

### 1. 演示材料

- [ ] 3—5 分钟演示视频，清晰展示项目定位、核心功能和技术亮点；
- [ ] 演示脚本，明确先说什么、后说什么、重点强调什么；
- [ ] 核心流程截图（6—10 张），带说明文字；
- [ ] 演示环境检查清单，确保演示过程稳定可靠；
- [ ] 备用演示方案（录屏 / 本地部署 / 截图）。

### 2. 答辩准备

- [ ] 答辩 PPT（10—15 页），突出架构图、核心流程图、关键界面截图；
- [ ] 答辩陈述稿（5—8 分钟），逻辑清晰、重点突出；
- [ ] Q&A 准备清单（10—15 个问题），并准备回答要点；
- [ ] 答辩反馈记录，记录教师建议和改进方向。

### 3. 个人贡献

- [ ] 个人贡献说明（1—2 页），明确职责、成果、问题和成长；
- [ ] 关键成果证据链接（Git 提交、文档、测试报告、演示视频）；
- [ ] 能力自评与教师评价对照表；
- [ ] 个人技术亮点清单（3—5 项，可写入简历）。

### 4. 简历与作品集

- [ ] 简历项目描述（2—3 条），使用 STAR 法则；
- [ ] 作品集链接清单（GitHub / Gitee / 演示视频 / 文档链接）；
- [ ] 面试表达脚本（30s / 2min / 5min 三个版本）；
- [ ] 常见面试问题与回答要点（10—15 条）。

### 5. 项目复盘

- [ ] 项目复盘报告（2—4 页），包含做得好、做得不好、学到什么、下次改进；
- [ ] 能力差距分析表，明确当前能力、目标能力、差距和弥补方案；
- [ ] 后续行动计划（3—6 个月），包括毕业设计、竞赛、求职等方向；
- [ ] 给未来团队的建议（如适用）。

## 十、AI 在本篇中的正确角色

AI 可以帮助你：

- 根据项目 README 生成演示脚本的初稿；
- 检查答辩 PPT 的结构是否完整、逻辑是否清晰；
- 分析个人贡献说明是否突出了关键成果；
- 优化简历项目描述的表达，使其更符合 STAR 法则；
- 生成常见面试问题的回答要点；
- 整理复盘报告的框架，确保四个问题都有覆盖。

但 AI 不能替代你完成：

- 实际录制演示视频；
- 真实回答答辩问题；
- 确认个人贡献的真实性和准确性；
- 验证简历描述与实际项目的一致性；
- 完成真实的自我反思和复盘。

!!! failure "不能把 AI 生成的内容当作自己的真实经历"
    演示视频、答辩陈述、个人贡献说明和复盘报告必须基于你的真实项目经历。虚构的成果、夸大的贡献或抄袭的复盘，不仅无法通过答辩，也无法在面试中经受追问。

## 十一、开始前准备

进入 6.1 前，请确认：

- [ ] 第五篇 `v1.0` 版本已完成，项目可运行、可部署、有测试报告；
- [ ] 项目 README 完整，包含启动说明和测试账号；
- [ ] 已准备好演示环境（本地部署或在线访问）；
- [ ] 已确定答辩时间和形式（线上 / 线下、个人 / 团队）；
- [ ] 已收集项目过程中的关键材料（Git 提交记录、设计文档、测试报告）；
- [ ] 接受“展示和复盘是项目的重要组成部分”，而不是额外负担。
