# 系统开发与阶段验收（System Development）

依据已确认的需求与设计逐阶段开发。先跑通最小核心业务闭环，再补齐其他必做与应做模块。**每次调用只完成一项工作**：编写里程碑文档，或完成**一个**里程碑阶段（如 M1）的开发与测试；完成后停下，等待用户确认或下达下一阶段指令，不连续推进多个阶段。每阶段完成实现、分层测试和实测记录后，依据验收结果决定是否进入下一阶段。

## 工作原则

1. **以确认基线为准**：开发依据来自已确认的《需求分析说明书》《系统设计说明书》和 HTML UI 原型；原型仅用于核对页面和交互，业务规则与验收条件以需求和设计文档为准。
2. **核心闭环优先**：先完成启动、数据库初始化与测试环境等必要基础，再打通一条从界面、接口到数据持久化的核心业务流程，随后扩展其余模块与异常分支。
3. **复用既有架构与框架**：已有项目先查看当前改动、既有目录结构、依赖配置、测试框架与运行方式，保留现有成果并记录已知失败。
4. **分层实测、真实留痕**：单元测试、接口测试与浏览器界面测试须在真实运行环境下执行并保留可复现证据，如实区分 `通过 / 失败 / 阻塞 / 未执行 / 不适用`。
5. **变更同步留档**：开发过程中若发现设计冲突或范围变更，先列明影响并确认，随后同步更新需求、设计、原型和里程碑记录。

## 使用流程

### 一、确认开发依据

- 读取最新的《需求分析说明书》《系统设计说明书》和 HTML UI 原型，提取必做与应做需求（`FR-*`）、业务规则（`BR-*`）、验收条件（`AC-*`）、页面（`UI-*`）、接口（`API-*`）、权限、状态及数据关系。
- 结合项目现有代码和运行说明确认技术栈、目录结构、依赖、启动命令与测试工具。
- 材料冲突或缺失影响当前实现时，列出具体问题及影响，先确认受影响范围，再推进可独立完成的工作。

### 二、划分开发里程碑（触发输入：根据需求、设计文档、UI设计稿 划分项目开发里程碑）

本次调用**仅产出里程碑文档**，不开始编写业务代码。按依赖和可演示的业务结果拆分里程碑（默认编号为 `M1`、`M2`…，里程碑计划保存至 `docs/development/milestones.md`，阶段测试记录保存至 `docs/development/test-records/M1.md`），按需读取[里程碑与测试记录模板](references/milestone-test-record.md)：

- 先列里程碑总览、预计工时、依赖关系和通用验证约定；
- 再逐阶段写明目标与范围、任务清单、交付物相对路径、覆盖**单元测试、接口测试、浏览器界面测试**的验证步骤以及**通过标准（DoD）**；
- 用已有 `FR / BR / UI / API / AC` 编号建立追踪关系（编号缺失时采用稳定的文档条目补充映射）；
- 涉及关键外部服务或 AI 链路时，尽早安排小范围验证以确认数据、权限和服务可用性。

### 三、按里程碑开发和测试（触发输入：根据里程碑文档，完成 M1 的开发测试）

单次调用只完成**一个**里程碑阶段（如 M1）：从里程碑文档确认本阶段范围，实现并完成本阶段测试留档后即收尾，不擅自扩展到 M2 及后续阶段。

1. **开始阶段**：读取现有计划和测试记录，确认前置条件与当前待验收范围；恢复中断任务时，以代码和实测记录确认真实进度。
2. **实现并自查**：从可运行的小改动开始，将业务规则落实到前端交互与后端入口；重点检查身份权限、数据权限、输入校验、状态合法流转、失败处理和数据一致性。
3. **执行分层测试**：按[阶段测试执行指南](references/testing-guide.md)运行单元测试、接口测试、浏览器界面测试以及受改动影响的已有流程回归。浏览器测试应实际打开运行中的系统执行操作，检查界面反馈与持久化数据变化；浏览器控制不可用时，记录阻塞原因并给出人工复测清单。
4. **修复、复测并留档**：对失败用例记录原因、修复动作与复测结果；保留测试环境、代码版本、命令或操作步骤、期望与实际结果、结论及日志/截图相对路径。
5. **确认阶段结论**：必做与当期应做功能完成且适用的必需用例全部通过后，更新里程碑状态为“已验收”；必需用例失败、阻塞或未执行时保持“待验收”，先修复或补测。本阶段结论确认后即结束本次调用，进入下一阶段须由用户再次触发。

### 四、完整回归与阶段交付

完整开发结束后，从可复现的初始化状态运行覆盖核心主流程与关键异常流程的最终回归测试，交付源代码、运行与数据库初始化说明、里程碑计划、阶段测试记录和最终回归结果，并明确剩余问题及复现方式。测试文件、日志与脱敏截图随项目按相对路径保存，清除真实凭据和个人信息。

## 单次调用输出要求

每次调用只交付以下**一项**结果，做完即停，等待用户下一步指令：

- **仅编写里程碑文档**：交付里程碑总览、依赖关系、通用验证约定与各阶段计划，不擅自开始编写业务代码；
- **完成一个里程碑阶段**：先确认前置条件与本阶段 DoD，实现后按阶段测试指南执行实测，交付代码变动、阶段测试记录与最新验收状态，不继续开发下一阶段；
- **恢复中断的单个阶段**：先盘点工作区改动、既有测试记录和已知失败项，输出进度基线后再继续本阶段未完成任务；
- **完整开发回归**：仅在全部里程碑开发完成、用户明确要求最终交付时，运行跨阶段回归测试，汇总最终交付清单、通过率与遗留问题。

## 禁止事项

- 不在单次调用中既规划里程碑又编写业务代码，也不在完成一个里程碑阶段后未经用户确认继续开发下一阶段；
- 不脱离需求与设计基线擅自扩充范围外的模块或复杂度；
- 不将未执行、阻塞或仅写了预期结果的测试用例标记为“通过”；
- 不以编译构建成功或静态代码检查代替接口测试与运行中的浏览器界面实测；
- 不编造测试运行日志、截图、接口返回或缺陷修复结果；
- 不在代码仓库、日志、测试数据或截图中留存真实密码、API 密钥与个人隐私信息。

## 交付前核对与下游交接

- [ ] 里程碑总览状态与各阶段测试记录、验收结论完全一致；
- [ ] 本期必做/应做需求（`FR-*`）、业务规则（`BR-*`）与验收条件（`AC-*`）均有对应实现与实测记录；
- [ ] 测试日志、脚本、报告与脱敏运行截图均使用有效的相对路径关联；
- [ ] 真实密钥与个人敏感数据已清理，只保留示例测试凭据。

请妥善保留里程碑计划（如 `docs/development/milestones.md`）、阶段测试记录（如 `docs/development/test-records/M*.md`）及脱敏运行截图；开发验收完成后，下一步可使用 `course-report` 技能将这些材料作为课程报告中系统实现与功能测试部分的直接实测证据（说明测试验收完成后如何衔接课程报告阶段时，必须在回复中显式写出下游技能名称 `course-report`）。
